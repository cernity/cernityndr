# Detection Capability Manifests

One versioned manifest describes each shipped detector **service**, including its
constituent finding detector IDs. These describe detection capability, distinct
from the [deployment capability manifest](../../deploy/central/capability-manifest.json)
(producer/topic/consumer wiring). Keep the two separate.

The contract is [detection-capability.v1](../../contracts/detection-capability.schema.json).
Discovery in the coverage test enumerates service directories ending in
`-detector` or `-detectors`, plus the named detection producers `ids-alerts` and
`threat-intel`, and requires an app entrypoint and Dockerfile. Adapters, file
processors and downstream finding services are outside this U2 inventory.
New shipped detector services following this convention automatically require a
manifest; extend the discovery aliases when introducing a differently named one.

All seeds are `shipped`, not `verified_e2e`: no backing golden-PCAP test is
established here. Beaconing, DGA, tunneling and TLS rarity remain explicitly
unverified end to end. Benign-control references are unit tests with negative
examples, not packet-replay evidence. General unit/state tests are linked in
`known_limitations` because the U1 schema has no general unit-test array; they
must not be mislabeled as performance or golden-PCAP tests. Empty arrays mean
no backing evidence is claimed for that test class. Paths are repo-relative.

ATT&CK entries come from explicit candidate `mitre` values or the existing
category fallback in [state_machine.py](../../services/finding-service/state_machine.py).
The latter is deliberately coarse (including HTTP's credential-access mapping).
No technique is inferred from a detector's name. `TA0010` is a tactic, so it is
omitted. Empty technique lists reflect absent mappings. Technique presence means
an implemented mapping, not e2e validation: limitations describe that distinction
without marking the same ATT&CK claim unverified, which would violate U1 KTD5.

`evidence_produced.record` links the finding contract for emitted
`ndr.finding.candidate.v1` records, not observations generated by the detector.
`input_records` lists consumed topics. Features and config parameters are selected
detection-relevant fields/tunables, not exhaustive runtime configuration.
No common observation-capability gate is implemented across these raw-EVE
consumers, so `required_capabilities` is empty; input/feature requirements and
visibility caveats are described separately.

`version` versions this manifest (initial 1.0.0), not every constituent detector.
`first_supported_version` is the current repository baseline, 0.0.1 from
`pyproject.toml`; it does not assert an earlier historical release date.
Measured quality belongs to [feedback-service/quality.py](../../services/feedback-service/quality.py)
(KTD2). Static manifests contain no live precision/false-positive metrics.

Run the contract and coverage gate from the repository root:

```sh
PYTHONPATH=shared .venv/bin/python -m pytest contracts/test_detection_capability.py contracts/test_detection_manifest_coverage.py -q
```
